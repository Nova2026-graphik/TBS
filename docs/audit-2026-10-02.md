# Audit du projet — 2 octobre 2026

Audit complet du dépôt `Nova2026-graphik/TBS`, branche `main` au commit
`25ad641`. Tout ce qui est affirmé ici a été **exécuté**, pas déduit : chaque
constat porte la commande qui l'a produit.

> **Suivi** — trois correctifs ont été appliqués depuis la rédaction de cet
> audit : le verrou (§2.1), la version de TypeScript (§2.4) et l'échappement
> du JSON-LD (§3.2). Les constats d'origine sont conservés tels quels ; chaque
> section porte son état courant.

- **Périmètre** : 170 fichiers source, 21 312 lignes (TypeScript, Vue, scripts).
- **Environnement de contrôle** : Linux x64, Node 22.22.0, npm 10.9.4.
  Le dépôt demande Node 24 (`engines`, `.nvmrc`) — tout compile et passe
  malgré l'écart, npm se contente d'un avertissement `EBADENGINE`.

## 1. Verdict

Le projet est **sain sur le fond et cassé sur l'outillage**.

L'application se construit, se sert et passe l'intégralité de ses tests : 141
tests unitaires et 81 parcours de bout en bout, tous verts, les seconds joués
contre la sortie de production réelle. L'architecture est nette, la sécurité
sérieusement traitée — en-têtes posés aux deux endroits qu'il faut, session
d'administration signée, limitation de débit en base, aucun secret versionné.

En revanche, **quatre des cinq étapes de vérification ne s'exécutent plus** :
l'installation reproductible, le lint, le contrôle de types et l'audit de
sécurité échouent tous, sur des causes de dépendances et non de code. Le filet
que le projet s'était donné faute de CI (`npm run ci`, crochet de pré-envoi)
tombe donc dès la première étape.

## 2. Anomalies bloquantes

### 2.1 — `npm ci` échoue : le verrou est désynchronisé

```
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json are in sync.
npm error Missing: oxc-parser@0.152.0 from lock file
… 86 entrées manquantes
```

`package-lock.json` ne décrit pas `oxc-parser` ni ses 85 binaires de
plate-forme, tirés par `@nuxt/content`. Conséquences en chaîne :

- l'étape « Installation » des trois travaux de `.github/workflows/ci.yml`
  échoue avant toute autre ;
- Vercel, qui utilise `npm ci` dès qu'un verrou est présent, échoue au build ;
- `npm run ci` et le crochet `.githooks/pre-push` s'arrêtent à la première
  étape, sans rien vérifier.

**Correctif appliqué.** `npm install` régénère le verrou. Le différentiel est
**purement additif** — 86 entrées ajoutées, 0 retirée, **0 version modifiée** :
aucune dépendance ne bouge, le verrou se contente de décrire ce que
`package.json` demandait déjà.

### 2.2 — `npm run lint` échoue : ESLint ne démarre plus

```
ESLint: 10.10.0
TypeError: Cannot read properties of undefined (reading 'Intrinsic')
    at node_modules/ts-api-utils/lib/index.cjs:787:57
    at node_modules/@nuxt/eslint-config/node_modules/@typescript-eslint/
       typescript-estree/dist/convert-comments.js:37:30
```

`ts-api-utils`, tiré par `@typescript-eslint`, lit une API interne du
compilateur que **TypeScript 7.0.2 ne publie plus**. Le crash est au
chargement : pas un seul fichier n'est analysé.

C'est le plus coûteux des trois, parce que `eslint.config.mjs` dit lui-même
pourquoi le linter existe ici : les règles `vuejs-accessibility`. Un `alt`
manquant, un `label` sans champ, un rôle ARIA inventé — la seule garde
automatique contre ces trois erreurs ne tourne plus.

### 2.3 — `npm run typecheck` échoue : `vue-tsc` ne démarre plus

```
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './lib/tsc' is not
defined by "exports" in node_modules/typescript/package.json
    at resolveTscPath (node_modules/vue-tsc/index.js:73:43)
```

Même cause. `vue-tsc@3.3.11` charge `typescript/lib/tsc`, un chemin que
TypeScript 7 n'exporte plus. Aucun type n'est vérifié, ni dans le code ni
dans les gabarits.

### 2.4 — Correctif commun à 2.2 et 2.3 — **appliqué**

`typescript: "^7.0.2"` (`package.json`, `devDependencies`) était en avance sur
l'écosystème : ni `vue-tsc` 3.x ni `@typescript-eslint` ne le supportent
encore. La dépendance est redescendue à `^5.9.0` ; version installée : 5.9.3.

```jsonc
"typescript": "^5.9.0",
```

**Résultat mesuré** : `npm run lint` rend 0 erreur, `npm run typecheck` rend 0
erreur. Le code n'était pas en cause — aucune ligne de source n'a eu à changer
pour les faire passer.

Le verrou ne bouge que de ce qu'il faut : `typescript` 7.0.2 → 5.9.3, et les
**20 binaires de plate-forme** `@typescript/typescript-*` disparaissent avec
lui — TypeScript 7 est le portage Go, qui les embarquait. `nuxt-component-meta`
cesse au passage de dédoubler sa propre copie de TypeScript. Aucune autre
version ne change.

À remonter le jour où `vue-tsc` et `typescript-eslint` annoncent TypeScript 7.

### 2.5 — `npm audit` : 19 avis, dont 13 « high » — *non traité*

L'étape CI `npm audit --audit-level=high --omit=dev` échouerait, et le README
affirme encore « doit rester à 0 vulnérabilité ».

| Paquet | Gravité | Chemin | Correctif |
| --- | --- | --- | --- |
| `devalue` | high (×3) | `nuxt` | `npm audit fix` — en place |
| `brace-expansion` | high (×2) | outillage | `npm audit fix` — en place |
| `serialize-javascript` | low | build | `npm audit fix` — en place |
| `node-forge` | high | `nuxt` → `selfsigned` (serveur de dév HTTPS) | demande `nuxt@3.15`, soit une **régression majeure** : à ne pas suivre |
| `phin` | moderate | `potrace` (devDep, `icons:trace`) | demande `potrace@2.1.1` : à ne pas suivre non plus |

Les trois premiers se règlent sans toucher à une version directe. Les deux
derniers ne sont atteignables qu'en dégradant le projet : ils ne concernent
que des outils de développement (serveur HTTPS local, vectorisation du logo),
jamais une surface servie en production. La position raisonnable est de les
documenter comme acceptés plutôt que de rétrograder Nuxt.

## 3. Anomalies fonctionnelles

### 3.1 — Toute requête `HEAD` sur l'API répond 404 — `/api/health` compris

Mesuré sur la sortie de production (`node .output/server/index.mjs`) :

| Route | `HEAD` | `GET` |
| --- | --- | --- |
| `/api/health` | **404** | 200 |
| `/api/branches` | **404** | 200 |
| `/api/faq` | **404** | 200 |
| `/api/gallery` | **404** | 200 |
| `/api/site-content` | **404** | 200 |

Les gestionnaires `*.get.ts` ne sont plus associés à `HEAD` par Nitro. Le cas
qui compte est `/api/health` : une route dont c'est toute la raison d'être
d'être interrogée par une sonde de supervision, et la plupart des sondes
(UptimeRobot, Better Stack, Pingdom) envoient un `HEAD` par défaut. La
supervision signalerait une panne permanente sur un site parfaitement sain.

**Correctif** — déclarer explicitement la méthode, par exemple en renommant
`server/api/health.get.ts` en `server/api/health.ts` avec un
`defineEventHandler` gardant lui-même les méthodes acceptées, ou en posant une
`routeRule` qui mappe `HEAD` sur `GET`. À vérifier d'abord sur la sonde
réellement retenue.

### 3.2 — Le JSON-LD n'échappe pas `<`, et une partie vient de la base — **corrigé**

`app/composables/useSeo.ts` (lignes 164, 175, 199) et
`app/pages/conseils/[slug].vue` (ligne 52) injectent le résultat de
`JSON.stringify(...)` dans l'`innerHTML` d'un `<script type="application/ld+json">`.

`JSON.stringify` n'échappe pas `<`. Une chaîne contenant `</script>` ferme donc
la balise et ce qui suit est interprété comme du balisage.

Ce n'est pas théorique ici : `useFaqSchema` est alimenté par
`server/utils/repository.ts:225`, qui lit la table `faq_items` — et l'édition
du contenu **sans redéploiement** est une fonctionnalité annoncée du projet.
Une réponse de FAQ saisie depuis Supabase devient donc un vecteur d'injection
persistante. La CSP limiterait la casse, mais elle est en `report-only` par
défaut.

**Correctif appliqué** — `shared/utils/jsonLd.ts` porte la fonction, appelée
aux quatre endroits :

```ts
export function serialiserJsonLd(donnees: unknown): string {
  return JSON.stringify(donnees).replaceAll('<', '\\u003c')
}
```

L'échappement JSON de `<` est strictement équivalent à `<` pour tout analyseur
JSON, les moteurs de recherche y compris : les données structurées restent
lues comme avant, mais plus aucune chaîne ne peut fermer la balise.

`tests/unit/jsonLd.spec.ts` garde le correctif en cinq points — la charge
`</script><img onerror=…>` neutralisée, tous les `<` échappés et pas seulement
le premier, les clés comme les valeurs, le JSON qui reste valide et porte les
mêmes données, et ce qui n'a pas besoin d'être échappé laissé intact.

### 3.3 — `.gitignore` : la dernière ligne annule l'exception de `.env.example`

```gitignore
# Environnement
.env
.env.*
!.env.example      ← exception
…
.vercel
.env*              ← dernière règle : elle reprend .env.example
```

Git applique la **dernière règle qui correspond**. `.env.example` n'est encore
suivi que parce qu'il l'était déjà avant l'ajout de cette ligne ; un
`git rm --cached` suivi d'un `git add` le ferait disparaître sans bruit — et
avec lui la documentation des 19 variables d'environnement.

**Correctif** — supprimer le `.env*` final, redondant avec les deux premières
lignes du bloc.

### 3.4 — Les messages d'erreur de Zod remontent en anglais

```
POST /api/quotes  {}
→ 422 { "name": "Invalid input: expected string, received undefined", … }
```

`server/utils/quoteValidation.ts` donne un message français à chaque contrainte
de **format** (`'Nom trop court'`, `'Numéro invalide'`…), mais pas aux champs
**absents** : Zod retombe alors sur son texte par défaut, et
`app/components/Contact/Form.vue:351` l'affiche tel quel sous le champ.

La validation côté client couvre `name`, `phone`, `email` et `message` avant
l'envoi : le cas n'est atteignable que sur `branch`, `requestType` ou
`details`, donc rare. Il reste visible le jour où il arrive.

**Correctif** — `z.string({ error: 'Champ obligatoire' })` sur les champs
requis, ou un `errorMap` global sur le schéma.

### 3.5 — `/sitemap.xml` répond par une page HTML

```
GET /sitemap.xml  → 307, content-type: text/html
<meta http-equiv="refresh" content="0; url=/sitemap_index.xml">
```

Le site étant bilingue, `@nuxtjs/sitemap` produit un index et deux sitemaps
(`fr-TG.xml`, `en.xml`). `robots.txt` pointe correctement sur
`/sitemap_index.xml`, donc **le référencement n'est pas affecté**. Mais
l'adresse conventionnelle que vérifie un humain, ou un outil de contrôle SEO,
rend du HTML. Une redirection 301 propre vaudrait mieux que la page de
rafraîchissement.

## 4. Points d'entretien

### 4.1 — Trois dépendances de développement déclarées et jamais utilisées

`@nuxt/test-utils`, `@vue/test-utils` et `happy-dom` ne sont importés nulle
part : aucun test de composant n'existe, et `vitest.config.ts` tourne en
`environment: 'node'`. Elles pèsent sur l'installation et sur la surface
d'audit sans rien garder.

Deux issues possibles, l'une ou l'autre : les retirer, ou écrire les tests de
composant qu'elles supposaient. Les parcours Playwright couvrent déjà le
rendu réel, ce qui plaide pour la première.

### 4.2 — L'intégration continue ne démarre toujours pas

107 exécutions du workflow `CI`, **aucun succès**. Chacune passe à `failure`
en trois à huit secondes, sans enregistrer une étape. Le diagnostic du README
tient : la cause est au niveau du compte GitHub, pas du fichier. Le chiffre,
lui, a vieilli — il annonçait 83 échecs.

Conséquence pratique : `npm run ci` et le crochet de pré-envoi sont le seul
garde-fou, et ils sont **inopérants tant que §2.1 à §2.3 ne sont pas réglés**.
C'est l'enchaînement qui rend ces trois anomalies urgentes plutôt que
gênantes.

### 4.3 — Seize informations légales manquent toujours

`shared/utils/legalData.ts` compte 16 champs à `value: null` — capital social,
RCCM, NIF, gérant, hébergeur, et les conditions de location (acompte, caution,
annulation, casse, zone de livraison). Les trois pages légales existent, sont
pré-rendues et affichent un marqueur « À compléter » visible, ce qui est le
bon comportement ; il reste que le site est en ligne avec des mentions
incomplètes. C'est une donnée à obtenir de TBS, pas un défaut de code.

## 5. Ce qui a été vérifié et tient

### Sécurité

- **En-têtes posés aux deux endroits**, vérifié sur le build réel : la page
  pré-rendue `/` porte les dix en-têtes, CSP comprise. C'est le piège classique
  du pré-rendu — page servie par le CDN, jamais vue par le serveur — et il est
  évité.
- **Espace d'administration éteint par défaut** : sans `NUXT_ADMIN_PASSWORD`,
  `/admin` et `/api/admin/*` répondent 404 (vérifié). Un déploiement qui oublie
  la variable n'ouvre pas un accès libre.
- **Session signée** HMAC-SHA256, comparaison à temps constant, cookie
  `httpOnly` + `SameSite=Strict` + `Secure` hors développement.
- **Limitation de débit en base** sur une fenêtre glissante, avec repli mémoire
  qui ne s'ouvre pas quand la base tousse ; les échecs d'authentification sont
  comptés séparément des réussites.
- **Adresse cliente jamais crue sur parole** : `trustedProxy` nomme
  explicitement ce qui est devant l'application, défaut prudent (`direct`).
- **Aucun secret versionné** : seul `.env.example` est suivi, aucune clé ne
  traîne dans les sources.
- **Courriels échappés** : `quoteNotification.ts` passe chaque valeur du
  formulaire par `escapeHtml` avant de la mettre dans le HTML du message.
- **Aucun `v-html`** dans l'application.

### Tests

| Unitaires (Vitest, 15 fichiers) | **141 / 141**, 1,67 s |
| Bout en bout (Playwright, 16 fichiers) | **81 / 81**, bureau et mobile, 1 min 18 |

Les parcours sont joués contre `node .output/server/index.mjs`, donc contre le

### Internationalisation

ni dans l'autre**. Les 19 valeurs identiques entre les deux langues ont été

« WhatsApp », « Lomé — Togo », « TBS Distribution »). Rien n'est oublié.

variantes d'images. Sortie de 49,3 Mo, 20,3 Mo compressés.
